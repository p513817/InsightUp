# 產品路線圖

這份路線圖反映目前產品狀態，以及後續最安全的建置順序。

## 已完成基礎

以下項目已是既有功能，不再視為待辦；後續開發應保留這些行為。

- 單一可部署的 Next.js App Router 應用程式
- Supabase Auth 與 Google OAuth
- Supabase SSR session 傳遞
- InBody 紀錄新增、讀取、更新、刪除
- 透過 `deleted_at` 進行預設軟刪除
- 圖表納入/排除與刪除分開處理
- 整體與分段圖表視圖
- 儀表板偏好設定
- AI 趨勢摘要支援快取/最新結果讀取，以及明確手動重新生成
- 以方案驅動的 LLM 權益解析
- AI 掃描草稿輸入，並維持先審核再儲存
- 好友代碼、好友快照與好友歷史紀錄
- 個人目標，支援負向進度
- 競賽功能，包含邀請成員、成員目標與排行榜進度
- Vercel 生產部署目標

## 第一階段：產品穩定化

目標：

- 讓既有功能更不容易因後續修改而退化。

任務：

- 擴充個人目標邊界情境測試，特別是零變化目標與負向進度。
- 補上競賽成員排序與鎖定目標日期的聚焦測試。
- 針對掃描權益與趨勢摘要權益路徑，增加 API 層或 route handler 測試。
- 每次修改 UI 文案時，同步維護 `messages/*.json` 的覆蓋。
- 補上行動版流程的 smoke-test 註記，尤其是底部操作列與浮動操作按鈕。
- TODO：在全面改版前，先執行小範圍 UI/UX 試點。先挑一到兩個介面，優先考慮登入/帳戶相關頁面與 AI 趨勢摘要彈窗。使用 Taste Skill 作為審核視角，檢查字體層級、間距、對比、行動版操作性，以及 loading/empty/error 狀態。必須保留既有產品規則、i18n keys、路由結構、圖表互動，以及 `components/ui/` 慣例。若試點能提升清晰度且不增加複雜度，再把同樣處理方式擴展到其他產品介面。

完成定義：

- 核心流程能搭配明確且聚焦的測試進行修改。
- 後續開發者能快速找到正確檔案入口，不必掃描整個 repository。

## 第二階段：通知與即時更新

目標：

- 在不讓 client 負責 fan-out 的前提下，通知使用者社交與競賽事件。

候選事件：

- 競賽邀請
- 成員接受或拒絕邀請
- 好友新增一筆 InBody 紀錄
- 好友或競賽成員達成目標，或目標進度退步

建議建置順序：

1. 新增 `notifications` table，以及站內通知列表/徽章。
2. 在既有 route handlers 或 RPC 附近的流程中，加入 server-side 通知建立。
3. 使用 Supabase Realtime 訂閱目前可見頁面的更新。
4. 新增 Web Push 訂閱儲存與推送。
5. 若產品價值明確，再加入交易型 email 備援。

完成定義：

- 使用者能看到持久化的站內通知。
- 競賽詳情頁能在成員狀態或目標變更時更新。
- Push/email 是選配，不是唯一資訊來源。

## 第三階段：AI 掃描儲存與審核深度

目標：

- 讓由掃描產生的紀錄可信且可稽核。

任務：

- 若產品需要後續審核，將上傳的掃描檔案存入持久化 storage。
- 將萃取 metadata 持久化到 `raw_extraction_json`。
- 改善紀錄表單中的欄位層級不確定性顯示。
- 考慮透過權益設定提供不同方案的掃描模型池。
- 掃描儲存必須維持使用者明確確認後才執行。

完成定義：

- 使用者能理解哪些掃描欄位是高信心推論。
- 品質不佳的掃描不會靜默污染圖表。

## 第四階段：社交與競賽優化

目標：

- 讓好友與競賽功能有實用價值，但不變成吵雜的排行榜噱頭。

任務：

- 改善競賽邀請生命週期與通知狀態。
- 針對尚未設定目標的受邀者，提供更清楚的空狀態。
- 新增好友紀錄通知偏好設定。
- 考慮競賽封存/已完成視圖。
- 改善建立者控制能力，同時保留成員隱私。

完成定義：

- 使用者能理解邀請中期待他採取什麼行動。
- 競賽資料仍限制在成員與 RLS 邊界內。

## 第五階段：分享與報告

目標：

- 將趨勢與目標進度轉成可分享的成果。

任務：

- 穩定分享頁輸出與截圖/匯出行為。
- 針對選定日期區間新增報告式摘要。
- 考慮分享指標的隱私控制。
- 除非明確另行設定，匯出內容應基於已納入圖表的紀錄。

完成定義：

- 使用者能產出有用的進度快照，且不暴露不相關的私密資料。

## 第六階段：商業化

目標：

- 讓方案權益、使用限制與帳戶 UI 對齊真實產品包裝。

任務：

- 將剩餘 feature fallback 邏輯移入 shared helpers 或 RPC。
- 只在方案模型穩定後才加入付款服務整合。
- 將帳戶頁從方案顯示擴充為方案管理。
- 新增權益調整的管理者/營運文件。

完成定義：

- 產品限制可從資料庫檢查。
- UI 與後端強制執行相同限制。

## 使用者要求前暫不處理

- 拆分成獨立 web/API services。
- AI 掃描直接自動儲存，不經審核。
- 硬編碼特殊使用者或 developer bypass。
- 以 app-only authorization 取代 Supabase RLS。
- 在站內通知歷史完成前，先建置 push/email delivery。
